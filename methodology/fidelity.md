# Backend fidelity — design and protocol

**What this measures:** whether an inference backend reproduces exact strings —
dates, amounts, IDs, UUIDs, JSON values — that the model was just shown.
Not quality, not reasoning. Copy fidelity only.

**Why it exists:** two open LiteRT-LM issues show accelerated backends corrupting
digits while CPU is clean on the same bytes — #2814 (iOS/Metal, Gemma 4, digit
sequences, 2026-07-11) and #3012 (Adreno 750, ~2k-token German prompts, corrupted
numbers and words, 2026-07-27). Both are silent: the output stays fluent, so
semantic evals miss it. No public mobile benchmark covers this class — AI Edge
Portal and Pipette measure speed/memory only. The failure classes here (digit
corruption, prefill hangs, per-turn leaks) are exactly what separates
"benchmarkable" from "shippable".

## The causal unit is a within-runtime backend A/B

A claim of the form "backend X corrupts digits" is only attributable when
**everything except the backend is held fixed**: same runtime build, same model
bytes, same tokenizer, same sampler, same prompt bytes — CPU vs GPU/NPU inside
one runtime.

Cross-runtime comparisons (LiteRT-LM vs llama.cpp vs MLX) are reported only as a
**scoreboard**, never as causal claims: each ecosystem runs its own quantization,
tokenizer implementation, and sampler, so a delta is not attributable to the
backend. This repo has already paid for that lesson once — the same Gemma-4
weights score 85% on LiteRT and 48% on fp16-activation runtimes purely from the
wNa8o8 co-design (see CLAUDE.md rule 2). Cross-runtime rows answer a different,
still useful question: *is the corruption class LiteRT-specific or Metal-wide?*
If llama.cpp's Metal backend passes the same suite the same model class fails on
LiteRT-LM Metal, that localizes the defect; if both fail, it points at shared
GPU numerics (fp16 accumulation) rather than one runtime's kernels.

## Suite form

Pinned artifact: `evaldata/fidelity_suite_v1.jsonl` (91 cases), generated by
`scripts/gen_fidelity_suite.py`, seed 20260901. The file is part of the protocol
(same rule as the pinned GSM8K set): regenerate only with a version bump.

Two task families, both trivially solvable so the CPU baseline sits near 100%:

- **copy** — one `REFERENCE: <payload>` line inside digit-free filler prose;
  instruction: output the line after the colon exactly.
- **extract_json** — 4 payload fields scattered in the filler; instruction:
  output a JSON object, values copied exactly as JSON strings. Doubles as the
  tool-argument-fidelity proxy without depending on any model's tool-call format.

Axes:

- **payload_class**: date_iso, date_text, amount, id_digits (15 digits), uuid,
  phone (NANP 555-01xx fictional range), order_id, version — digit-dense values,
  seeded per case id.
- **context_bucket**: 128 / 1024 / 2048 / 4096 estimated prompt tokens.
  Context length is a *trigger variable* — #3012 appears at ~2k — so it is swept,
  not fixed.
- **position**: early / middle / late payload placement (KV-depth effect).
- **lang**: en, plus de (the #3012 shape: German filler at 1k–4k) and ja.
- **tier**: smoke (8, pipeline debug) ⊂ core (49, the claim set) ⊂ full (91).

Invariants, asserted at generation time: filler prose contains **no digits**
(every digit in an output traces to the payload); each payload appears exactly
once; case ids are unique; generation is byte-deterministic from the seed.

## Run protocol

- **Greedy** (topK 1, temp 0). Remaining run-to-run variance *is* backend
  nondeterminism, which is measured, not averaged away: reps N per case
  (smoke 2–3, core 10, full 20), reporting both pass-rate and distinct-output
  count. #2814 was intermittent; single-shot runs cannot see it.
- **One long-lived engine per arm**, one conversation per generation, with the
  global sequence number recorded (`engine_seq`) — corruption and leaks can be
  state-dependent (the Pixel 7 per-turn leak), and a long-lived engine is how
  real apps run.
- **Total-context sizing**: for LiteRT-LM, `maxNumTokens` is *total context*,
  and undersizing it **corrupts output instead of truncating** (CLAUDE.md rule
  3) — a fidelity harness that got this wrong would manufacture its own
  positives. The runner sizes it from the largest included case
  (`est × 1.35 + budget + 64`, rounded up to 128) unless overridden.
- **Hang policy**: per-generation timeout (default 300 s). On timeout the runner
  records the event, exits 3, and treats the engine as poisoned (the #2814-class
  hang does not cancel); `--resume` continues a run from the recorded position.
- Runners record actual prefill/decode counters where the runtime exposes them;
  `est_prompt_tokens` is only a sizing estimate.

## Scoring (`scripts/fidelity_score.py`)

Per-field classification, priority order:

1. **PASS** — expected string present verbatim.
2. **DIGIT_CORRUPT** — the format skeleton matches (punctuation/layout intact)
   but digits differ. The #2814 signature and the headline metric.
3. **FORMAT_DRIFT** — digit sequence intact but formatting changed (separators
   dropped, date rewritten). A fidelity failure, semantically intact.
4. **MISSING** — value absent; flags EMPTY / DEGENERATE (loop heuristic shared
   with `quality_check.py`) / ERROR.

**Claims gate (refute-first):** a case enters the backend-delta table only if
the same arm's **cpu** backend passes it in ≥90% of reps. A case the model
cannot do on CPU is a capability limit, not a backend bug, and is reported
separately. The publishable claim shape is:

> On {runtime} {version}, {model}, {device}: {backend} fails N of M
> claim-eligible cases that cpu passes, with K DIGIT_CORRUPT generations
> (examples: `2033-01-10` → `2033-01-17`). Repro: suite file + runner command.

What is deliberately **not** claimed: cross-runtime superiority, root cause
(kernel vs scheduler vs quant interaction), or fleet-wide incidence.

## Boundary with sibling harnesses

Three tools by the same author answer three different questions — keep them
separate and cross-linked, or from outside they read as duplicates:

- **litertlm-release-gate** — *does what a user installs today generate at
  all?* Per-channel, per-release; canary generation checks pipe health, and
  structurally cannot see fluent-but-wrong output.
- **this suite** — *does the backend reproduce values correctly?* Per-backend,
  statistical (greedy × reps), catches exactly what the gate passes through.
- **edge-llm-bench** — *how fast, how long?* Performance and endurance.

Planned integration: a smoke/core fidelity run per release feeds one PASS/FAIL
row into the gate's table, adopting the gate's vocabulary (PASS/FAIL/SKIP;
every FAIL maps to an upstream issue number); device-matrix arms (Android)
ride edge-llm-bench's device fleet.
