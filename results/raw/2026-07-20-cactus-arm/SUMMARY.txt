Integration difficulty (fairness rule 5 — recorded, not folded into scores):
  * Their swift surface is a modulemap over cactus_engine.h; the xcframework
    `apple/build.sh` produces bundles ONLY that header, whose first include is the
    C++ cactus_graph.h -> `import cactus` cannot compile as shipped. The FFI decls
    never reference graph types; vendoring strips the include (bootstrap.sh).
  * Bundle graphs embed the converter machine's ABSOLUTE weight paths
    (/Users/jakmro/dev/cali/…); the engine falls back to bundle_dir/basename only
    when that file exists -> any incompletely-copied bundle fails at cactus_init
    with the converter's path in the error.
  * devicectl `copy to` of the 3.8 GB / 2030-file bundle SILENTLY dropped 219 files
    (exit 0) — the missing-file sweep in this session's notes is mandatory device
    prep. (That is our tooling's trap, not Cactus's, but it presents as the above.)
    A name-level sweep is NOT enough: a second pass found 19+14 size-TRUNCATED
    files (incl. embed_tokens_per_layer / ffn_down) — verify sizes via
    pymobiledevice3 house_arrest and rm-then-rewrite.
  * cactus's messages parser is KEY-ORDER-SENSITIVE: parse_messages_json only
    searches for "content" after "role". JSONSerialization randomizes dict order
    per process -> ~half of app launches sent content-first JSON and the engine
    silently generated from an EMPTY user turn (prompt_tokens=9 = bare gemma-4
    template, "Please provide the text…" answers). First capture pass invalidated
    (3/4 short-chat + 1/2 deep-context); adapter now hand-serializes role-first
    (commit 2b4a342). Python/json.dumps clients never hit it (insertion order) —
    which is why every Mac GSM8K number stands. Any order-randomizing serializer
    (Swift, some Kotlin configs) hits it silently.
